# مستودع GPS التحليلي — المشروع الثاني (00380)

مشروع Supabase منفصل يحمل **الجزء الثقيل فقط** من GPS: السحب الشهري الخام، محرّك التوقفات، البقع، والأرشيف المضغوط.
التشغيلي الحي ومسارات الانطلاقيات تبقى في المشروع الأول. المتصفح **لا يتصل** بهذا المشروع أبداً؛ الوصول حصراً من دالة الحافة
`gps-warehouse` في المشروع الأول بمفتاح الخدمة.

## الربط مرة واحدة (بالماوس)
1. **المشروع الثاني** → SQL Editor → الصق محتوى `supabase/migrations/0001_warehouse_schema.sql` → Run.
2. **المشروع الثاني** → Project Settings → API Keys → Secret keys → أنشئ مفتاحاً جديداً (لا تستخدم أي مفتاح سبق لصقه في محادثة أو رسالة).
3. **المشروع الأول** → Edge Functions → Secrets → أضف:
   - `GPS_WAREHOUSE_URL` = `https://<ref>.supabase.co` (رابط المشروع الثاني بلا `/rest/v1/`)
   - `GPS_WAREHOUSE_SERVICE_KEY` = المفتاح السرّي من الخطوة 2
4. بوابة IT → التكاملات → سلامة تكامل GPS → بطاقة «مستودع GPS التحليلي» → **فحص الاتصال** ثم **إرسال سجل الآليات**.

> بديل الخطوة 1 للجولات القادمة (اختياري): `npx supabase link --workdir gps-warehouse --project-ref <ref>` مرة واحدة، ثم `npx supabase db push --workdir gps-warehouse` مع كل جولة.

## الجولة 00381 — محرّك السحب
- طبّق `supabase/migrations/0002_pull_engine.sql` على المشروع الثاني (SQL Editor أو `db push --workdir gps-warehouse`).
- المجدول في المشروع الأول (`00325`) يستدعي `gps-warehouse` بـ `{"action":"pull"}` كل دقيقة عبر Vault (`project_url` / `edge_service_role`) — إن لم تكن أسرار Vault موجودة فطبّق `docs/GPS_PUSH_SCHEDULER_SETUP_AR.md` ثم أعد `db push`.
- كل دورة: 3 مهام (جهاز × يوم) على قطع 3 ساعات من LVN، إدخال في `wh_raw_points`، حساب توقفات اليوم فوراً في `wh_stops`، أرشفة الأيام المنجزة مضغوطة في دلو `gps-archive`، وحذف الخام الأقدم من 3 أيام.
- الأرشيف: `YYYY/MM/YYYY-MM-DD/<device>.json.gz` — `{v, device, day, cols:[epoch,lat,lng,speed,course], points:[[...]]}`.

## الجولة 00382-أ
- طبّق `0003_ping_storage.sql` على المشروع الثاني (SQL Editor): الفحص يضم حجم التخزين وعدد الملفات ⇒ تظهر قاعدة المستودع وتخزينه في لوحة المساحة ببوابة IT.
- في المشروع الأول (هجرة `00328`): نقاط GPS التفصيلية تُفرَّغ كلياً كل يوم 00:00 بغداد — البند في وحدة الأرشيف ← GPS.

## الجولة 00382-ب — النافذة الشهرية المتجددة
- طبّق `0004_rolling_window.sql` على المشروع الثاني (SQL Editor).
- القاعدة: المعروض = الشهر السابق؛ الجاري يُجمَّع يوماً بيوم تلقائياً (يوم الأمس يُجدول مع كل دورة للمجدول، on conflict do nothing)؛
  أول كل شهر يُمسح ما قبل `cutoff` (= أول يوم الشهر السابق عند `keep_months = 1`): مهام + خام + توقفات، وملفات الأرشيف تُحذف من التخزين.
- الخام يُحذف فور اكتمال توقفات اليوم (`raw_retention_days = 0`)، الأرشيف المضغوط معطّل (`archive_enabled = false`).
- لا حاجة لزر «جدولة سحب الشهر» في التشغيل العادي؛ يبقى للتعويض اليدوي داخل النافذة فقط (`WH_MONTH_EXPIRED` لما قبلها).

## الجولة 00383 — محرّك البقع
- الصق `0005_hotspots.sql` في محرر SQL للمشروع الثاني (بعد 0004). التجميع يجري تلقائياً مع كل دورة صيانة (كل دقيقة): يُسنَد كل توقف **صالح** (10 دقائق – ساعتان) لأقرب بقعة ضمن 80 م أو تُنشأ بقعة جديدة، ثم تُعاد حسابات البقع المتأثرة.
- الأصناف: خفيف ≤ 20 د، متوسط ≤ 60 د، ثقيل أكثر (الصنف الغالب للبقعة). التكرار: مرة واحدة < 3 أيام، متكرر 3–9 أيام، شبه يومي ≥ 10 أيام مميزة. كل الحدود في `wh_settings` وتظهر في بطاقة IT.
- كل ليلة 23:30 بغداد يستدعي مجدول المشروع الأول `sync_hotspots`: يُنسخ **الملخص فقط** (بقع الشهر المعروض والشهر الجاري) إلى `gps_hotspots` في المشروع الأول؛ لا نقاط ولا توقفات خام تُنقل. البقع خارج النافذة تُحذف في المشروعين.

## الجولة 00386-ب — مراقبة السحب
- الصق `0006_monitoring.sql` في محرر SQL للمشروع الثاني (بعد 0005). يضيف إلى `wh_progress()`: ملخص الأخطاء حسب الرمز (`error_summary`)، الأجهزة الأكثر فشلاً (`failed_devices`)، العالقة (`stale_running`)، والسرعة/التقدير العامّين (`throughput`)، ودالة `wh_retry_failed(p_month)` لإعادة المهام الفاشلة نهائياً إلى الطابور (داخل النافذة فقط؛ خدمة فقط).
- في بطاقة IT: قسم «الأخطاء حسب السبب» مع شرح عربي لكل رمز، زر «إعادة محاولة الفاشلة»، ملخص المساحتين، وزر «نسخ تقرير التشخيص» لإرسال لقطة الحالة نصاً.
