# دخول الموظفين ودعم الحسابات — جزيرة الأكارم

## التدفق الحالي

1. صفحة الموظفين عادت إلى واجهة GitHub `main` القديمة (مكونات `LoginBackground` و`LoginForm`)؛ أضيف زر/أيقونة سماعة للدعم يفتح صفحة مساعدة الدخول الحالية. لم يُعَد ضبط بقية المستودع إلى `main` لأن ذلك سيزيل تغييرات كثيرة خارج نطاق تسجيل الدخول.
2. دخول الموظف يمر عبر Edge Function `staff-login` ثم يحفظ الجلسة في Supabase JS client كالسابق (`persistSession: true`, refresh token محفوظ). تُوجّه الأدوار عبر `resolvePortal`.
3. الخادم يحتسب فشل بيانات الاعتماد الحقيقي فقط: **10 إخفاقات خلال 15 دقيقة → قفل 5 دقائق للبريد + معرّف جهاز المتصفح الذي أخفق**. نجاح الدخول يمسح عدّاد الزوج نفسه. لا يُقفل الحساب على كل الأجهزة.
4. المتصفح لا يسجل الإخفاقات؛ يخزّن فقط موعد قفل أعاده الخادم لأجل العدّ التنازلي. الجدول `login_source_locks` يخزن HMAC لمعرّف الجهاز ولا يخزن كلمة المرور أو عنوان IP.
5. مسارات `record_login_attempt` و`is_login_locked` القديمة سُحبت صلاحية تنفيذها من `anon` و`authenticated` حتى لا يستطيع العميل اصطناع الإخفاقات أو فحص القفل القديم. لا تستخدم RPC قديمة للاختبار اليدوي.

## دعم الدخول وكلمات المرور

- وحدة الدعم: `/it/login-support`؛ يتحقق الخادم من JWT ودور `it_admin` لكل إجراء إداري.
- تشمل صندوق المحادثة/طلبات المتابعة، إعداد رقم الهاتف وساعات التواصل، حالة توفر الفريق، عرض الأقفال وفكها لبريد الموظف بعد التحقق، والبحث عن الهاتف المسجل لإجراء إعادة ضبط.
- طلبات المحادثة تستخدم رمز متابعة عشوائياً؛ لا يستطيع المتصفح قراءة الجداول مباشرة (RLS مفعّل، الوصول عبر Edge Function فقط). رسائل المحادثة لا ينبغي أن تحتوي كلمات مرور أو رموزاً سرية.
- إعادة الضبط لا تعرض كلمة المرور الحالية (Supabase لا يستطيع إرجاعها). موظف الدعم يتحقق باتصال إلى الهاتف المسجل، يعيّن كلمة جديدة عبر مسار IT القائم، ثم يبلغ الموظف بها هاتفياً؛ لا تُرسل كلمة المرور في المحادثة أو البريد أو سجل التدقيق.
- صفحة تفاصيل المستخدم تشترط تأكيداً يدوياً للاتصال بالرقم المسجل قبل تفعيل زر إعادة الضبط. إذا لم يوجد رقم مسجل، تُمنع العملية حتى تحديث بيانات الاتصال.
- `forgot-password` و`reset-password` يعرضان طريق الدعم ولا يقدمان نموذج تغيير ذاتي.

## حدّ Supabase المعروف والموافق عليه

هذا منع على مستوى التطبيق ومساراته، وليس حظراً على واجهة Auth العامة: أي مستخدم يملك جلسة مصادقة يستطيع نظرياً استدعاء Supabase Auth API مباشرةً خارج التطبيق. Supabase لا يوفر منعاً حسب الدور لـ `auth.updateUser({ password })`. اتُّفق على إزالة تدفق التغيير الذاتي من الواجهة الحالية مع توثيق هذا القيد؛ الإغلاق الكامل يتطلب قراراً معمارياً أوسع.

كذلك معرّف الجهاز UUID محفوظ في `localStorage` ويمكن للمستخدم المتقدم تغييره/مسحه؛ لذلك فهو تقسيم مصدر عملي للتطبيق وليس بصمة جهاز لا يمكن التحايل عليها. محاولات البيانات الخاطئة لا تُحتسب إلا بعد رفض Supabase Auth الفعلي، والحدود الأصلية لـ Supabase تبقى طبقة إضافية.

## تغييرات قاعدة Supabase الفعلية

- `20261108193000_staff_login_support.sql`: جداول قفل الجهاز/طلبات الدعم/الرسائل/الإعدادات، دوال عداد خادمية لا ينفذها إلا `service_role`، وRLS بلا وصول مباشر لـ`anon` أو`authenticated`.
- `20261108193500_revoke_legacy_login_rpcs.sql`: إبطال صلاحيات RPC القديمة.
- Edge Functions المنشورة: `staff-login` و`login-support` (`verify_jwt=false` لأن الأولى دخول عام، والثانية تتحقق من الدور داخلها لإجراءات الإدارة).
- قائمة CORS المضبوطة تسمح بالنطاقين المحليين، ونطاق التجربة `https://akram.example.iq`، ومعاينات `e2b.app`، وأصل معاينة Arena الدقيق `https://arena.ai`. لا يُسمح بـwildcard؛ اضبط النطاق الفعلي للإنتاج قبل الإطلاق.

## نتائج الفحص الحالية

- في استعادة الواجهة القديمة: الاختبارات المحددة `LoginPage.test.tsx`, `login-guard.test.ts`, `auth.sdk.test.ts` نجحت **16/16**، وفحص ESLint للملفات الثلاثة المعدلة نجح بلا تحذيرات. اختبار المتصفح على 390×844 دخل بحساب `it_admin` إلى `/it` عبر `staff-login` (HTTP 200)، حُفظت الجلسة ثم سُجّل الخروج بنجاح، بلا أخطاء صفحة أو طلبات شبكة. فشل `npm run typecheck -- --pretty false` بسبب نفاد ذاكرة Node (OOM)، فلا توجد نتيجة typecheck ناجحة.
- شُغّلت المعاينة في Chromium فعلي بعد تجهيز المكتبات محلياً: سطح المكتب (1440×900) والهاتف (390×844)؛ كلا التخطيطين ظهر، والعنوان/الصورة/النموذج سليمة، لا أخطاء JavaScript، لا تجاوز أفقي، واحترام `prefers-reduced-motion` تحقق. إرسال نموذج فارغ أظهر «البريد الإلكتروني مطلوب» من دون استدعاء تسجيل الدخول. فُتحت نافذة الدعم واختُبر حبس التركيز وإعادته.
- الفحص البصري كشف تراكباً مؤكداً في نسخة سطح المكتب (نص زر وروابط مرسوم على الصورة مع تكرار عناصر التحكم). أُصلح بتعديل CSS محدد، وأُعيد التصوير: لم يعد النص مكرراً، ثم نجحت الاختبارات المستهدفة مجدداً.
- كان سبب تعطل بدء الدالتين متوافقاً مع استيراد `@supabase/supabase-js` عبر عنوان `esm.sh` في بيئة Deno؛ استُبدل بصيغة `npm:@supabase/supabase-js@2` الموصى بها في Supabase، وصُحّح تعريف نوع عميل الدعم. بعد إعادة النشر (`staff-login` إصدار 4، `login-support` إصدار 3)، نجح `deno check`، وأعادت كلتا الدالتين `OPTIONS 200` مع CORS صحيح. أعاد `staff-login` لمدخل فارغ `400 INVALID_INPUT` (قبل Auth ولا أثر جانبي)، وأعادت `login-support/public_settings` `200`؛ اختبار المتصفح أكد أن نافذة الدعم تقرأ الإعدادات بلا أخطاء CORS.
- اختبار دخول حي عبر نموذج المعاينة: حساب الموظف التجريبي دخل بنجاح إلى `/employee`، وحساب `admin_ops` التجريبي إلى `/admin-ops`. الحساب الفعلي `admin@akram.iq` موجود ومؤكد وغير محظور، ودوراه `it_admin` و`ops_room`؛ نجح دخوله إلى `/it`، حُفظت الجلسة ثم سُجّل الخروج للتنظيف، ولم تظهر أخطاء Console. لم تُعدّل كلمات مرور أو أدوار أو بيانات الحساب. الحساب الاصطناعي المنفصل `test-itonly-…` أعاد 401 للقيم التي جُرّبت؛ بلا جلسة، وسجلّا إخفاق منفصلان بلا قفل نشط.
- أظهر تصوير المستخدم أن صفحة الدخول مفتوحة ضمن `https://arena.ai`. قبل التعديل، أعاد اختبار `OPTIONS` لـ`staff-login` بلا `Access-Control-Allow-Origin` لهذا الأصل (بينما نجح محلياً لأن `localhost:5173` مسموح)، وهو ما يطابق رسالة «تعذر الاتصال بخدمة الدخول». أُضيف الأصل المحدد إلى سر `ALLOWED_ORIGINS`، وأعيد فحص `OPTIONS` حياً لكل من `staff-login` و`login-support`: كلاهما `200` ويعيد `Access-Control-Allow-Origin: https://arena.ai`. لم يُجرَ طلب دخول إضافي أثناء فحص CORS.
- إعداد الدعم المنشور حالياً يعيد `is_online=false` ولا يحتوي رقم اتصال، لذا لا يظهر رابط اتصال هاتفي حتى يضبطه `it_admin` من الوحدة.
- تعذر إنهاء `tsc -b` خلال 15 دقيقة؛ أُوقفت العملية. كما تعذر إنهاء إنتاج Vite bundle بسبب استهلاك الذاكرة/التعليق في مرحلة بناء الحزم. لا توجد نتيجة typecheck أو production build ناجحة.
