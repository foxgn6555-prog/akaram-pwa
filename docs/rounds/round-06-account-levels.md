# الجولة ٦ — صلاحيات الصفحات لكل حساب بثلاثة مستويات

**التاريخ:** 2026-11-19 · **الفرع:** `arena/0065458d-akaram-pwa`
**الحالة:** منفّذة ومختبرة محلياً — **لم تُدمج ولم تُنشر**.

---

## ١) الهدف

تنفيذ البند ٩: صلاحية **لكل حساب** — لا لكل دور — بثلاثة مستويات، منفّذة في الخادم وفي الـ API لا بإخفاء أزرار:

| المستوى | المعنى | ما يُسمح |
|---|---|---|
| **كامل** | `full` | عرض + إنشاء + تعديل/اعتماد/حذف |
| **إنشاء** | `create` | عرض + إنشاء فقط، بلا أي تعديل لاحق |
| **عرض فقط** | `view` | قراءة وتصدير فقط، بلا أي كتابة |

---

## ٢) القرار المعماري (الأهم في هذه الجولة)

النظام القائم (00294/00371) يجيب سؤالاً ثنائياً: «هل يملك الحساب الإجراء على الوحدة؟» عبر دالة واحدة يحكم بها كل شيء: `app.can`.

بدل تعديل مئات دوال الكتابة، أضفنا **طبقة سقف فوق نفس الدالة**:

```
app.can = app.can_base (المنطق القديم كما هو)  ثم  app.level_permits (السقف الجديد)
```

وبما أن كل دوال الكتابة تنادي `app.require_can` ⇒ `app.can`، و`my_permissions()` تُبنى من `app.can` أيضاً:

- **الخادم** يرفض أي كتابة تتجاوز السقف (`PERMISSION_DENIED`) قبل أي أثر.
- **الـ API والواجهة** يعكسان السقف تلقائياً (الأزرار تختفي لأن الصلاحية نفسها لم تعد تُعاد).

هذا يعني: **نقطة إنفاذ واحدة**، بلا استثناءات منسيّة، وبلا لمس أي دالة قائمة.

## ٥) أثر عملي مباشر

1. تقنية المعلومات تفتح «الصلاحيات» ← «صلاحيات الصفحات لكل حساب».
2. تبحث عن الحساب، تختار البوابة، تضبط كل صفحة (كامل / إنشاء / عرض فقط) أو تُزيل السقف.
3. الأثر فوري: الواجهة تُخفي الأزرار عند أول تحديث للصلاحيات، والخادم يرفض أي محاولة تجاوز حتى لو استُدعيت الدالة مباشرة (API bypass).
4. كل تعديل يُسجَّل في سجل تدقيق الصلاحيات باسم المنفّذ.

---

## ٦) حدود

1. **بلا سقف = كامل**: كل حساب يعود إلى سلوكه القديم تماماً حتى يُضبط له سقف. لا تغيير تلقائي على أي حساب.
2. **السقف يقيّد ولا يمنح**: لا يمكن فتح صفحة لحساب لا يراها من دوره.
3. `it_admin` مستثناة (قرار مقصود) — الحساب الذي يضبط السقوف لا يُقيَّد بها.
4. السقف على مستوى **الوحدة** (الصفحة) لا على مستوى سجل واحد؛ «تعديل سجلات قسمي فقط» يبقى في نطاق الأدوار.
5. لا إشعار للعضو عند تقييد صلاحياته (يمكن إضافته في الجولة ٧ إن أردت).
