## ① نتائج البحث — أجهزة البصمة ZKTeco (بروتوكول ADMS Push)

**المرجع:** وثائق ZKTeco PUSH SDK الرسمية v2.4.1 + مكتبات ADMS مفتوحة المصدر (Go/Python/Node)

### كيف يعمل (بدون IP ثابت — الجهاز هو من يتصل بنا!):

```
الجهاز (ZKTeco) ──HTTP──▶ خادمنا (Edge Function: adms-receiver)
   │  ① التسجيل الأولي:  GET /iclock/cdata?SN={الرقم التسلسلي}&options=all&pushver=2.4.1
   │     ردنا الإلزامي:   GET OPTION FROM: {SN}
   │                      ATTLOGStamp=0 · OPERLOGStamp=0 · Realtime=1
   │                      ServerVer=3.0.1 · Delay=5 · TransFlag=111111111111
   │  ② نبض القلب:       GET /iclock/getrequest?SN={SN}  ← كل ~5 ثوانٍ
   │     ردنا:            "OK"  (أو أمر بانتظار التنفيذ)
   │  ③ رفع الحضور:      POST /iclock/cdata?SN={SN}&table=ATTLOG&Stamp={n}
   │     الجسم (نص خام):  {PIN}\t{التاريخ الوقت}\t{الحالة}\t{تحقق}\t...
   │     مثال:            2  2026-08-27 09:01:33  255  15
   │  ④ تنفيذ الأوامر:   POST /iclock/devicecmd?SN={SN}&ID={n}   الجسم: "OK"
```

### رموز الحالة في سجلات الحضور:
| القيمة | المعنى |
|--------|--------|
| 0 | حضور (Check-in) |
| 1 | انصراف (Check-out) |
| 2 | خروج استراحة |
| 3 | عودة استراحة |
| 4/5 | دخول/خروج عمل إضافي |

### القرار المعماري:
- **Edge Function واحدة** (`adms-receiver`) تستقبل كل نقاط النهاية الأربعة — تتحقق من SN في جدول `biometric_devices` ثم تخزن الخام في `biometric_pushes` وتحول السجلات لـ `attendance_records` (ربط PIN → employee).
- إعداد الجهاز من صفحة التكاملات: نعرض رابط الخادم للنسخ في إعدادات الجهاز + نسجل SN.
- الأوامر الخارجة (إضافة مستخدم للجهاز مثلاً) عبر طابور `device_commands` يُسلَّم عند نبض القلب.

## ② نتائج البحث — تتبع الشاحنات GPS (تكامل مع كل الأنواع)

**المرجع:** Traccar (المعيار المفتوح — 200+ بروتوكول، 2000+ جهاز) + بروتوكول OsmAnd HTTP + وثائق Webhooks الرسمية

### الاستنتاج الحاسم:
معظم مزودي التتبع (بمن فيهم المزودون المحليون) يعملون إما **على Traccar** أو قادرون على **إعادة توجيه Webhook**. لذا مستقبِل **عام بصيغتين** يغطي كل الأنواع عملياً:

### الصيغة ① — Webhook بمعايير Traccar (JSON):
```json
{
  "position": { "deviceId": 10, "latitude": 33.31, "longitude": 44.36,
                "speed": 45.6, "course": 180, "fixTime": "2026-08-27T10:15:30Z",
                "attributes": { "ignition": true, "fuel": 67.2, "motion": true } },
  "device":   { "uniqueId": "123456789012345", "name": "شاحنة 01", "status": "online" }
}
```
### الصيغة ② — OsmAnd HTTP GET (أبسط صيغة عالمية — يفهمها أي جهاز):
```
GET /functions/v1/gps-receiver?id=TRUCK-01&lat=33.31&lon=44.36&speed=45&timestamp=...
```
### الأحداث: `deviceOnline/Offline` · دخول/خروج نطاق جغرافي (Geofence) · تجاوز سرعة

### القرار المعماري:
- **Edge Function** (`gps-receiver`) تستقبل الصيغتين + مفتاح API لكل مزود (`integration_providers`).
- جداول: `gps_providers` (المزود + نوعه + مفتاحه) · `vehicles` (الشاحنة ↔ معرف الجهاز ↔ الفرع) · `vehicle_positions` (آخر موقع + سجل مسار) · `gps_events`.
- عرض حي لاحقاً في بوابة العمليات — التجهيز التقني كامل في بوابة IT.

## ③ نتائج البحث — مصفوفة صلاحيات الصفحات (منح/إخفاء/قفل فردي)

**المرجع:** أنماط RBAC المعتمدة (Deny-by-default · User-override · Navigation filtering)

### النمط المعتمد (مؤكد من الأبحاث):
1. **الرفض افتراضياً** (Deny by default) — لا وحدة ظاهرة إلا بمصدر صلاحية.
2. ثلاث طبقات بأولوية حاسمة:
   - `role_page_permissions`: منح/إخفاء **لدور** (تعلو الافتراضي)
   - `user_page_overrides`: قفل/فتح **لشخص** (يتجاوز الدور — الحكم الأخير)
3. **الشريط الجانبي يبني نفسه بالفلترة** (نمط `filterNavigationByRole` الموثق): الوحدة تُخفى إن لم يبقَ أي صفحة مسموحة منها — والوصول المباشر بالرابط يُصدّ في الحارس أيضاً.
4. **تدقيق كل تغيير صلاحيات** إلزامياً (نمط Audit everything).

### مفتاح الصفحة (Page Key):
كل صفحة تحمل مفتاحاً ثابتاً مثل `it.users.list` — مرجعها الثابت في الكود، بينما منحها/إخفاؤها بيانات في DB.

## ④ القرار المعماري — البوابات الديناميكية (النموذجان معاً)

| النموذج | التنفيذ |
|---------|---------|
| **تركيب من المكتبة** | البوابة الجديدة = اسم + أيقونة + لون + اختيار وحدات/صفحات **جاهزة من المكتبة** (نفس مفتاح الصفحات) + منح دور جديد أو قائم |
| **بوابة فارغة** | نفس الشيء لكن بلا صفحات — تظهر «قيد البناء» ويملؤها المطورون لاحقاً بإضافة مفاتيح صفحات جديدة |

- `dynamic_portals` + `portal_units` (بيانات) — تُعرض في شاشة اختيار البوابات والمبدّل بجانب البوابات الثابتة.
- **خط أحمر أمني:** الصفحات الفعلية مكونات كود مسبقة — لا توليد كود من DB إطلاقاً.

## 🗄️ خريطة الجداول الجديدة (الجولة 2 — الأساس)

| الجدول | الوحدة | أعمدته الجوهرية |
|--------|--------|------------------|
| `branches` | الفروع | name · code · city · address · is_active |
| `employees.branch_id` | الفروع | FK — الموظف ينتمي لفرع |
| `role_page_permissions` | الصلاحيات | role · page_key · effect(grant/hide) |
| `user_page_overrides` | الصلاحيات | user_id · page_key · effect(allow/lock) |
| `dynamic_portals` | البوابات | slug · name · icon · color · is_active |
| `portal_units` | البوابات | portal_id · unit_key · label · icon · sort |
| `biometric_devices` | البصمة | serial_number · name · branch_id · last_seen · is_active |
| `biometric_pushes` | البصمة | الخام (logging قبل التحويل) |
| `gps_providers` | GPS | name · type · api_key · webhook_url |
| `vehicles` | GPS | plate · name · branch_id · device_unique_id · provider_id |
| `vehicle_positions` | GPS | vehicle_id · lat · lon · speed · ignition · fix_time |
| `integration_logs` | التكاملات | provider_id · direction · payload · status |
| `system_settings` | عام | key · value (إعدادات ديناميكية) |

كلها: RLS (IT فقط للإدارة) + فهارس + updated_at + تدقيق.
