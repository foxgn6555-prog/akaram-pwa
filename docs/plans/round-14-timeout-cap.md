# الجولة ⑪ — سقف الوقت ٨ ثوانٍ ⇒ ١١٠ + تحصين الدفعات

> **التاريخ:** ٢٠٢٦-١١-١٩ · **الفرع:** `arena/f49ad6a1-akaram-pwa`
> **الحالة:** مكتمل ومُختبَر — الغلاف طُبّق على الإنتاج بقياس. **لم يُسجَّل في
> `schema_migrations` ولم يُدمج** (بطلب صريح).

---

## ① العَرَض

```
⚠ تعذّر إكمال العملية
canceling statement due to statement timeout
```
و`Failed to load resource: 500` على `…/map_import_batch`. **لا يُدرَج شيء.**

## ② الجذر

```
pg_roles:  anon          => statement_timeout=3s
           authenticated => statement_timeout=8s     ← ← ←

pg_proc:   public.map_import_batch   => search_path فقط
           app.map_import_batch      => search_path فقط
           app.map_import_batch_impl => search_path فقط
```

**سقف المستخدم ٨ ثوانٍ ولا شيء يرفعه.**

## ③ الإصلاح

| الطبقة | ماذا |
|---|---|
| **سقف الوقت** | `SET statement_timeout = '110s'` على `public.map_import_batch` |
| **التحصين** | `try/catch` **داخل** حلقة الدفعات — الفاشلة تُسجَّل ويُكمَل الباقي |
| **العرض** | قسم أحمر يعرض «دفعة لم تُدرج» بمداها وسببها |

**لماذا ١١٠ لا ١٢٠؟** السقف العالمي ١٢٠ ثانية؛ ١١٠ يترك عشراً للـrollback قبل أن يقطع
الخادم الاتصال.

**لماذا على الغلاف فقط؟** ترتيب `SET` على دوال متداخلة غير موثوق. الخاصية على الأبعد كافية
وتُورَّث. (تحقّق حيّ: دالة بـ`statement_timeout='12s'` تُرجع `12s` من `current_setting`.)

## ④ 🔴 الاكتشاف الكبير: التدهور **تربيعي**

بعد رفع السقف، قِيس الإدراج فعلياً فظهر:

| الصفوف | الزمن | مللي/صف |
|---|---|---|
| 25 | 0.63 ث | 25.4 |
| 50 | 2.37 ث | 47.3 |
| 75 | 5.30 ث | 70.7 |
| 100 | 9.50 ث | 95.0 |

**المضاعفة تُضاعف الزمن ٣.٧×** ⇒ **O(n²)**، لا O(n).

### السبب

```sql
-- map_overlap_check()، trigger على كل إدراج
for r in select * from app.map_nearby_streets(new.zone_id, new.path, new.id)
```

`map_nearby_streets` تجلب **كل** صف ضمن ٦٠٠ متر — ومنها الصفوف **المُدرجة للتوّ في
نفس الدفعة**. فالصف رقم n يقارن بـ(n-1) ⇒ مجموع `n(n-1)/2`.

**التحقق الحسابي:** ١٠٠ صف ⇒ ٤,٩٥٠ زوج × ~٢ms (بعد الجولة ⑩) ≈ ٩.٥ ث ✓ مطابق.

### وقياس مضادّ حاسم

**٤ دفعات × ٥٠ = ٢٠٠ صف ⇒ ١٣.٣٨ ثانية.**

أي أن **كل دفعة أبطأ من التي قبلها**، لأن الصفوف **تتراكم في الزون**. فالتربيعية على مستوى
**الزون كله** لا الدفعة.

⇒ **تقسيم الدفعات لا يُصلح السبب.** (خفضتُ `batchSize` إلى ٥٠ للتوازن فقط، مع تصريح
صريح في الكود أنه تخفيف لا إصلاح.)

## ⑤ الأثر الفعلي

| الصفوف | الزمن | السقف ١١٠ ث |
|---|---|---|
| ٥٠ | ٠.٦ ث | ✓ |
| ١٠٠ | ٩.٥ ث | ✓ (كانت تُلغى!) |
| ٢٠٠ | ~٣٨ ث | ✓ |
| ٣٠٠ | ~٨٥ ث | ✓ (بطيء) |
| ٤٥٠ (زون كامل) | ~١٩٠ ث | ✗ يتجاوز |

**رفع السقف يمنع رسالة ٥٠٠** — وهذا هو العَرَض الذي شكا منه المشغّل. لكن **الأداء يبقى
سيئاً**، والإصلاح البنيوي جولة مستقلة.

## ⑥ ما لم تُصلحه هذه الجولة — بصراحة

**O(n²) باقية.** الإصلاح يحتاج واحداً من:

- **(أ) حارس دفعات**: علمٌ يمرّره الاستيراد يتجاوز فحص التطابق (المصدر OSM موثوق، والتحرير
  اليدوي يبقى محروساً).
- **(ب) فهرس مكاني حقيقي** (PostGIS) بدل `bbox &&` الخطي، مع استثناء صفوف الدفعة
  نفسها بـ`created_at`.

كلاهما جولة مستقلة. **خلطهما هنا كان سيجعل التراجع غامضاً.**
